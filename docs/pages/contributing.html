Contributing Guidelines

Thank you for your interest in contributing to GatiFleet. We welcome contributions that improve performance, expand neural agent solvers, or optimize user interface layouts.

Development Process

  1. Fork & Clone: Fork the GatiFleet repository and clone it to your local environment.
  2. Branching: Create a new feature branch using a descriptive name: 
    git checkout -b feature/driver-allowance-rules
  3. Local Code Check: Ensure code conforms to eslint standards by running: 
    npm run lint
  4. Commit Guidelines: Commit your changes using descriptive commit messages: 
    git commit -m "feat(dwip): calculate allowances from FASTag logs"
  5. Pull Request: Push changes to your fork and submit a Pull Request to the main branch of GatiFleet.

Testing Local Telemetry

To verify telematics maps and event pipelines locally without physical IoT devices:

  • Start GatiFleet in full-stack mode (refer to the Quick Start Guide).
  • Open the Fleet Tracking dashboard at http://localhost:5173/tracking.
  • Click the "Simulate Route" toggle to feed mock coordinates via Socket.io channels, verifying geofence alerts and P&L updates occur downline.

SLA and Policy Standards

When extending GatiFleet modules or adding new database tables, ensure compliance with GatiFleet guidelines:

  1. Never update data directly from buttons: Every operator interaction must emit an L1 event.
  2. Link transactions: Every new order or tracking entry must update the client's digital twin brains and graph relationships.
  3. Audit Trails: Maintain audit timestamps and operator references on database changes.
